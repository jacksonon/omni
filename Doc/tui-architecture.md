# TUI 渲染架构（OpenTUI 命令式渲染深度记录）

> 2026-08-26 从 `AGENTS.md` 迁移。含 OpenTUI 踩坑结论、布局预算数学、细胞池复用、浮层坐标、宽度判宽对齐、交互设计等实现级细节——**修改 TUI 前必读**。

### TUI 渲染（src/tui/，重要背景）

> **为什么不用 OpenTUI 的 solid 集成？** 踩坑结论：`@opentui/solid` 的 JSX 转换依赖 preload 注册插件，而**入口文件在插件注册前就被转换**（bun 的时序问题），JSX 被编译成 react 风格（静态求值），信号变更完全无法触发重绘（`createEffect` 一次都不执行）。bunfig preload、动态 import + 手动 `plugin()`、Bun.build + 显式插件均无法修复。
>
> **当前方案（命令式渲染）**：直接用 `@opentui/core` 的 renderable（BoxRenderable/TextRenderable/InputRenderable）构建渲染树，状态变更后显式调用 `renderer.loop()` 重绘（与测试库 renderOnce 内部机制一致）。确定性强、无响应式魔法。
>
> 关键点：
> - `state.ts` 是纯可变对象（lines[]/status/model/version），不是 signal；
> - 内容行用**细胞池复用**（非全量重建）：池只增不减，行数变化只切 `visible`，行内容原位更新 `content/attributes/fg`——每个 TextRenderable 持有原生 TextBuffer，早期「每帧 remove+new」会耗尽原生对象池（实测 ~1365 次重绘后 `createTextBuffer` 抛错且内容区被清空），复用后一次会话只分配一次、永不耗尽；
> - 布局：根 Box（`flexGrow:1` 撑满视口，**无边框/无标题**），内容行 → 状态栏 → **灰色块**（可选）→ **统计行**；灰色块用 `marginTop:auto` 吸收剩余空间，**始终钉在视口最底部**（内容从顶部增长，超出尾部窗口后自动裁剪）；内容行用 `insertBefore` `alignItems:'stretch'`，**无 paddingX**）：**左侧蓝色细线 `▍`（与对话流用户消息左侧同款，`marginLeft:-1` 盖住同色边框格、紧贴灰块左缘；**竖跨整个灰色背景含上下圆角边框行**——内容 = inputLines + 4（边框 2 + 输入 + 间距 + 模型），显式 height 钉住 + `marginTop/Bottom:-1`（负 margin 使 margin-box = inputLines+2 与内容列同高不撑大灰块，渲染起点上移 1 行盖顶边框、下溢到底边框；左缘两角 ╭╰ 被蓝线覆盖、右缘 ╮╯ 圆角保留），由 repaintTree 每次按最新 inputLines 同步）**；内容列（`paddingX:1`，**paddingY 0**——用户要求输入区域高度低：灰块 = 圆角边框 2 + inputLines + 间距 1 + 模型 1 = inputLines+4）内：多行 Textarea + **模型行（左对齐）**——`Build/Plan · 模型名 组名 · 思考级别`（footerModel + footerEffort，模式前缀（/plan 计划模式显示 Plan，普通 Build）+ 模型名与 provider 组名 + 思考级别，无「模型/思考」字样——用户要求；思考级别**按强度着色** `effortColor`（theme.ts `effortColors`：low 绿 → medium 琥珀 → high 橙 → xhigh 红 → max 紫，深色 400 档 / 亮色 600 档，未知/自定义级别回退 footerDim，/variants
